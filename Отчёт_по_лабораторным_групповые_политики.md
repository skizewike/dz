# Лабораторная работа №1
**Тема:** Управление конфигурацией среды исполнения ПО с помощью ручного программирования системных политик реестра (Windows Home/Pro).

## Цель
Разобраться, как групповые политики работают под капотом, и научиться включать/выключать их без графического редактора — прямо через `reg`. Заодно смоделировать реальную задачу из практики: запрет записи на съёмные носители (например, чтобы внедряемый софт нельзя было использовать как канал утечки данных).

## Ход работы

### Шаг 1. Базовое состояние

Воткнул флешку, создал на ней текстовый файл `test.txt` — всё записывается, никаких проблем. Открыл командную строку от имени администратора. **Скриншот №1** — консоль администратора и файл на флешке.

### Шаг 2. Включаем политику через reg

Выполнил одной строкой:

```
reg add "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices\{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}" /v Deny_Write /t REG_DWORD /d 1 /f
```

Консоль ответила `Операция успешно завершена`.

GUID `{53f5630d-b6bf-11d0-94f2-00a0c91efb8b}` — это не случайный набор букв, а идентификатор класса устройств «съёмные диски» в ядре Windows. Параметр `Deny_Write = 1` включает запрет записи.

Дальше перезапустил проводник, чтобы система перечитала политики:

```
taskkill /f /im explorer.exe
start explorer.exe
```

Рабочий стол моргнул и вернулся. **Скриншот №2** — вся последовательность команд в консоли.

### Шаг 3. Проверка

Захожу на флешку, пытаюсь создать файл — Windows выдаёт «Вам отказано в доступе». Чтение при этом работает как обычно: файлы открываются, копируются с флешки на диск. То есть перехватилось именно обращение на запись, а не доступ к носителю целиком — поведение в точности как у доменной политики. **Скриншот №3** — диалог с отказом в доступе.

### Шаг 4. Демонтаж политики

Убрал ключ:

```
reg delete "HKLM\SOFTWARE\Policies\Microsoft\Windows\RemovableStorageDevices" /f
```

Снова перезапустил проводник. Флешка записывается как раньше. Точку восстановления использовать не пришлось — откат штатный.

## Вывод по ЛР №1
Групповая политика — это не магия и не отдельная программа. Это ключи реестра в строго определённых ветках (`HKLM\SOFTWARE\Policies\...`), которые служба `gpsvc` читает и применяет. Если знать нужный раздел и параметр, gpedit.msc не нужен вообще — политику можно и поставить, и снять из командной строки. Именно так и приходится работать на Windows Home.

# Лабораторная работа №2
**Тема:** Диагностика результирующих конфигураций (RSoP) и аудит применения политик безопасности средствами PowerShell.

## Цель
Научиться снимать с системы актуальную картину применённых политик и настроек безопасности — в виде отчётов и через конвейеры PowerShell.

## Ход работы

### Шаг 1. Сбор данных через gpresult

Открыл PowerShell от имени администратора.

```
New-Item -ItemType Directory -Path "C:\GP_Reports"
gpresult /x C:\GP_Reports\gpreport.xml /f
```

XML-отчёт создался. **Скриншот №1** — окно PowerShell с командами.

### Шаг 2. HTML-отчёт

```
gpresult /h C:\GP_Reports\report.html /f
```

Открыл `report.html` из проводника. В браузере — «Данные групповой политики», раскрыл сводку. Отчёт большой, но читается нормально: видно, какие настройки применились к компьютеру. **Скриншот №2** — открытая сводка отчёта.

### Шаг 3. Парсинг настроек через PowerShell

Веб-отчёт хорош для глаз, но для быстрого анализа удобнее вытащить конкретные параметры напрямую:

```
Get-LocalUser | Select-Object Name, Enabled, PasswordRequired, LastLogon
```

Получил таблицу локальных учёток: имена, включены ли, требуется ли пароль, когда последний раз логинились. Для софта, который работает с БД и учётками, это базовая информация — например, если программа стартует под отключённой учёткой, сразу видно, где искать.

Второй запрос:

```
Get-ItemProperty -Path "HKLM\SYSTEM\CurrentControlSet\Services\luafv" | Select-Object Start, DisplayName
```

Проверил состояние службы виртуализации файлов UAC (`luafv`). **Скриншот №3** — вывод обеих команд.

## Вывод по ЛР №2
`gpresult` даёт статичную картину применённых политик в удобном виде (XML для машин, HTML для людей), а PowerShell-конвейеры позволяют достать конкретный параметр за секунду, не листая простыню отчёта. Для диагностики «почему софт не стартует на этом ПК» связка `gpresult` + `Get-ItemProperty` закрывает большинство вопросов.

# Ответы на вопросы для защиты

## 1. Почему изменения в HKLM\SOFTWARE\Policies\ сработали как полноценная групповая политика, хотя gpedit.msc в Windows Home нет?

Потому что gpedit — это всего лишь редактор, удобная оболочка. Саму работу делает не он, а служба «Клиент групповой политики» (`gpsvc`), которая при загрузке системы и при обновлении политик читает ветки `HKLM\SOFTWARE\Policies\` и `HKCU\SOFTWARE\Policies\` и применяет их как правила. На домашней редакции служба никуда не делась — отключён только графический редактор и доменная часть (GPO из Active Directory). Поэтому если знать точный раздел и параметр (как наш `Deny_Write` для съёмных дисков), можно записать ключ в реестр напрямую через `reg add` — и служба воспримет его как политику точно так же. По сути мы вручную проделали то, что gpedit делает за администратора автоматически: создали ключ в правильной ветке.

## 2. Какую проблему совместимости решает служба luafv (виртуализация UAC)?

Проблему старых программ, которые рассчитаны на Windows XP и пишут данные в защищённые системные каталоги — `C:\Program Files`, `C:\Windows\System32`, ветку `HKLM` в реестре. Под XP любой пользователь мог писать куда угодно, а начиная с Vista эти области доступны только с правами администратора, и UAC блокирует запись.

Если такая программа запускается без повышения прав, служба luafv не даёт ей упасть с ошибкой «Access denied»: она перехватывает попытку записи и прозрачно перенаправляет её в изолированную песочницу пользователя (например, `C:\Users\<имя>\AppData\Local\VirtualStore`). Программа «думает», что записала файл в Program Files, а на деле файл лежит в виртуальном хранилище. То есть это шим совместимости для неопытных или ленивых разработчиков, которые жёстко прописали пути к системным папкам: софт продолжает работать, система остаётся защищённой, а данные пользователя не смешиваются с системными.

## 3. Что такое результирующая политика (RSoP) и зачем использовать gpresult при развёртывании ПО?

RSoP — это итоговый набор параметров, который реально получил конкретный компьютер после наложения всех политик по правилу LSDOU (локальные → сайт → домен → OU → вложенные OU). На итог влияет порядок применения, наследование, блокировки и фильтры безопасности, поэтому «что написано в GPO» и «что реально применилось» — не всегда одно и то же.

При развёртывании нового программного комплекса `gpresult` нужен именно для того, чтобы смотреть итог, а не предполагать его: открываем отчёт и видим, какие GPO фактически применились, какие параметры выиграли при конфликте, а какие не применились и почему. Если, например, корпоративный софт не может открыть порт или ему мешает AppLocker-правило, RSoP показывает, какая именно политика это сделала, — и чинится конфликт за минуты вместо перебора всех GPO домена вручную.
